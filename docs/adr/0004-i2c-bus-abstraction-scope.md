# Add a shared I2C register-access module; defer SPI2 abstraction

Five of the six I2C drivers (`axp2101`, `pcf85063a`, `bhi260ap`, `drv2605`, `xl9555`) each defined their own near-identical `read_regs()`/`write_regs()` static wrapping `i2c_master_transmit()`/`i2c_master_transmit_receive()`, with an inconsistent, mostly-unnamed timeout (a bare `100` literal in four of them; only `bhi260ap` named its outlier `BHI260_I2C_TIMEOUT_MS 1000`, undocumented). We extracted this into a new `components/drivers/i2c_bus/` component (`i2c_bus_read`/`i2c_bus_write`, free functions over the plain `i2c_master_dev_handle_t`, explicit `timeout_ms` per call) and migrated all five drivers to it. Each driver keeps its own named timeout constant, now passed explicitly rather than copy-pasted as a magic number - the design doesn't hide the 100ms-vs-1000ms split, it documents it. `axp2101_read_reg`/`write_reg`'s public signature (called directly by `main/debug/debug_cmds.c` for a raw-register debug dump) is unchanged; only each driver's internal `.c` file changed.

`i2c_bus_write` transparently handles both shapes found in the wild: small fixed writes (every driver except BHI260AP, previously stack buffers up to 8 bytes) and BHI260AP's dynamically-sized, heap-allocated writes (FIFO/firmware-upload transfers up to ~100KB) - previously duplicated by hand inside `bhi260ap.c`'s own I2C write callback, now the same code path as everyone else's single-byte pokes.

While auditing the buses we also found two dead/shadow device handles: `twatch_sd_spi_dev` and `twatch_touch_dev` were registered in `twatch_board.c` but never read anywhere - the real SD and touch traffic goes through separate handles ESP-IDF's own vendor helpers (`esp_vfs_fat_sdspi_mount`, `esp_lcd_new_panel_io_i2c`/`esp_lcd_touch_new_i2c_cst9217`) create internally on the same bus/CS/address. Checked ESP-IDF's source (`esp_driver_sdspi/src/sdspi_host.c`, `esp_lcd/i2c/esp_lcd_panel_io_i2c.c`): neither vendor helper accepts a pre-existing device handle, so there's no way to make the board's handle the real one. Deleted both dead handles and their now-unused pin/address `#define`s (`TWATCH_PIN_SD_CS`, `TWATCH_I2C_ADDR_TOUCH` - both already duplicated at their real owners, `sd_log.c`'s `SD_CS_GPIO` and `cst9217.h`'s `CST9217_I2C_ADDR`) rather than restructure around a limitation that doesn't have a workaround.

## Considered Options

- **Also abstract SPI2 now** (the board's other bus, shared by SD/LoRa/NFC): rejected for this pass. SD's SPI2 usage is entirely mediated by the vendor `sdspi`/VFS layer (no raw-transaction call site exists to migrate). LoRa (`sx1262.c`) and NFC (`st25r3916.c`) are unimplemented stubs (`ESP_LOGW(..., "not implemented")`) with zero real transaction code to design against - abstracting SPI2 today would mean guessing its shape (raw byte transfer vs. register-addressed, how BUSY/RESET/IRQ GPIO sequencing composes with a wrapper) with nothing to validate the guess against. Revisit once either driver has a real implementation.
- **A wrapper struct** (`i2c_bus_dev_t { dev, default_timeout_ms }`) instead of free functions taking the plain handle: rejected - `debug_cmds.c` calls `axp2101_read_reg`/`write_reg` directly with the raw `i2c_master_dev_handle_t`, and `twatch_board.c`'s global handle table is untyped `i2c_master_dev_handle_t` throughout. A wrapper type would force those call sites to change too, for no benefit five thin register-access functions need.
- **Retry-on-failure logic in `i2c_bus`**: not added - no driver has ever shown evidence of needing a retry (no bus-lock contention bug exists; ESP-IDF's own `i2c_master` driver already serializes transactions internally). The one-line-per-call interface leaves room for a future `i2c_bus_read_retry(...)` variant without touching existing call sites, but building it now would be speculative.
